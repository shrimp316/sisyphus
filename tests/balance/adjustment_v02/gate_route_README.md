# G123 full-route witness and actual-XP campaign probe

This separate probe is limited to **generation 6 / v0.2** experiments. It calls the source-derived production `_step_v02` at exactly 120 Hz, bypassing only the observer wrapper. It must not be used for other physics generations. Production scripts, progression costs, save files, and physics state after initial run setup are not changed.

`gate_route.gd` is an ideal exact-state policy, not a human model. It uses the existing optimized policy outside the gate, clears authored pre-gate shelf ledges at low speed with Shift, stops and heals on the existing shelf, then uses normal/coast at target 1.795 m/s to enter the gate. In 750–873 m it targets 1.195 m/s and uses Shift when normal force is insufficient. It knows the experimental gate's location. Purchases consume actual Progression points only at a stationary shelf; subsequent attempts preserve XP/ranks and generate a fresh seed. Menus, loading, choice deliberation, and retry UI time are excluded. Timeouts are censored and stop campaigns.

Run from the repository root (replace `$Godot` with the Godot 4.5.1 console executable):

```powershell
& $Godot --headless --path . --script tests/balance/adjustment_v02/gate_route.gd -- --config tests/balance/adjustment_v02/gate_route_campaigns.json --output NEW_DIRECTORY/routes.jsonl
& $Godot --headless --path . --script tests/balance/adjustment_v02/gate_route_replay.gd -- --input NEW_DIRECTORY/routes.jsonl
python tests/balance/adjustment_v02/audit_gate_routes.py NEW_DIRECTORY/routes.jsonl --output NEW_DIRECTORY/audit.json
```

Use a **new output directory** for each policy revision. Each run includes one byte per 120 Hz input step in a gzip file (bits: push 1, exert 2, brace 4), its SHA-256, the initial progression/physical ranks, candidate, seed, and final physical/progression snapshots. Metadata contains the complete policy source and its hash. Replay reads actual input bytes rather than recomputing decisions, and verifies physical and progression endpoints. Check the replay result count as well as zero failures; an empty selected job does not constitute a replay test.

Evidence under `tests/balance/results/act1-adjustment-v02/`:

- `gate-route-fixed-efficient-entry.jsonl`: fixed rank zero and three successful growth combinations, one clear-weather seed each. All four input streams replay exactly. This predates the ledge-aware policy branch; its policy source is embedded in metadata.
- `gate-route-campaigns/`: superseded exploratory campaigns. Normal-only pre-gate acceleration became stuck on existing 747.14 m ledges in some seeds. These timeouts describe a policy defect, not a proof of route impossibility. Original traces are preserved.
- `gate-route-campaigns-ledge-aware/`: final six actual-XP campaigns, 72 attempts, with raw inputs. Three balanced seeds plus one seed per strength/endurance/recovery-priority strategy. Each worker has its own replay result JSON.
- `gate-route-campaign-summary.json`: reproducible trace/economy/continuity audit and campaign observations, generated by `audit_gate_routes.py`.

Campaign `experiment_case` is `repeat_campaign_actual_xp_gate_oracle`. Its first run is the separate first-attempt-with-growth observation: unlike fixed zero fixtures it can buy earned upgrades during the run. High-rank fixed fixtures are reachability witnesses, not earned progression claims. Neither these successes nor failures alone establish impossibility; the separate resource-bound proof has its own assumptions.
